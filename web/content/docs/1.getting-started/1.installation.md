## Requirements

- **Paper 26.3** or newer, or **Velocity 4.3** or newer.
- For a network on several backends: a **MariaDB, MySQL or PostgreSQL** database that every
  backend can reach. A single server can use the built-in H2 file database.
- Optional: **LuckPerms** for the `LUCKPERMS_WEIGHT` exemption provider.
- Optional, on Velocity: **SignedVelocity**, so mutes can cancel signed chat (see below).

## Proxy or backends, never both

Install SakuraBans **either on the Velocity proxy or on every Paper backend, never on both**.
Each platform enforces bans and mutes on its own; running both would apply every punishment
twice and the two would not know about each other.

### On the proxy

One instance serves the whole network. Put the jar into the proxy's `plugins/` folder and
restart it.

- Server scopes follow the player: a punishment for `server:bedwars-1` applies while the player
  is on that backend. `enforcement.enforce-server-switch` decides whether switching servers is
  checked.
- Mutes are enforced on the proxy, for chat and for the commands in
  `enforcement.mute-command-blacklist`. Since Minecraft 1.19.1 a proxy can only cancel signed
  chat with the **SignedVelocity** plugin installed. Without it, SakuraBans logs a warning at
  startup and lets muted players' chat (and commands with signed arguments) through, because
  denying them would disconnect the player. Commands that can be cancelled safely are still
  blocked.
- Names that were never seen are not looked up on a proxy.

### On the backends

Put the jar into `plugins/` on every Paper server, and point all of them at the same
MariaDB, MySQL or PostgreSQL database in [`storage.yml`](/docs/configuration/storage). Turn on
`sync.mode: SQL` so a ban on one backend reaches players on the others within seconds.

- Give each backend its name in `server.name` ([config.yml](/docs/configuration/config#server)),
  the name the network knows it by, so `server:<name>` and category punishments apply there.
- Read [Networks](/docs/guides/networks) for what must match between backends.

## The first start

On the first start SakuraBans creates its folder (`plugins/SakuraBans/` on Paper,
`plugins/sakurabans/` on Velocity) with these files, copied from the defaults:

| File | What it holds |
|---|---|
| `config.yml` | Behaviour: scopes, enforcement, alts, reasons, exemption, warnings, display, the editor address, command labels |
| `storage.yml` | The database connection, table prefix, pool and sync |
| `limits.yml` | Staff groups with maximum durations, cooldowns and required templates |
| `templates.yml` | The seed for templates (read once into the database) |
| `webhooks.yml` | Discord webhook routes |
| `import.yml` | Where `/sb import` reads other plugins' data |
| `lang/en_US.yml` | Every message, in MiniMessage |

With the defaults, SakuraBans uses an H2 file (`sakurabans.mv.db`) in its folder.

**SakuraBans never rewrites these files.** Your comments survive; keys added by newer versions
use their defaults until you add them, and the log lists them at startup. If a value is
invalid, SakuraBans refuses to start and lists every problem with its key path.

## Changing settings

- Edit the file and run `/sb reload`. If anything is invalid, the old settings stay active and
  you get the list of problems.
- `storage.yml` and `commands.labels` need a restart.
- On a network, settings, messages and templates can also be set network-wide in the database,
  through the [web editor](/docs/web-editor). Such an override wins over the file;
  `/sb settings list` and `/sb messages list` show them.
