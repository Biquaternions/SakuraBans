Changes to `storage.yml` need a restart; `/sb reload` keeps the current storage and says so.

Every key can also come from the [environment](/docs/configuration/environment), which wins over
the file: `SAKURABANS_STORAGE_HOST`, `SAKURABANS_STORAGE_POOL_MAXIMUM_SIZE`, ... or one JSON
object in `SAKURABANS_CONFIG`.

| Key | Default | Meaning |
|---|---|---|
| `type` | `H2` | `H2` (a local file, the default), `MARIADB`, `MYSQL` or `POSTGRESQL`. Several servers sharing one MariaDB, MySQL or PostgreSQL database share their punishments. |
| `h2.file` | `sakurabans` | The H2 database file, in the plugin folder and without extension (`sakurabans` becomes `sakurabans.mv.db`). Only used with `H2`. |
| `host` | `localhost` | Database host (ignored with H2). |
| `port` | `0` | `0` uses the database's default port (3306, or 5432 for PostgreSQL); otherwise 1-65535. |
| `database` | `sakurabans` | The name of the database, which must already exist. |
| `username`, `password` | `sakurabans`, `''` | Credentials. |
| `table-prefix` | `sb_` | Prepended to every table name, so several plugins or networks can share a database: 1-16 characters of a-z, 0-9 and `_`, starting with a letter. Changing it later points SakuraBans at new, empty tables. |
| `schema` | `''` | PostgreSQL schema, a lower-case name; empty uses the default (`public`). |
| `properties` | `{}` | Extra JDBC connection properties of the driver in use, as `name: 'value'` pairs, for example `useSSL: 'true'`. |
| `address-hash-key` | generated | The secret key that turns IP addresses into keyed hashes (HMAC-SHA-256), at least 32 characters. See [below](#address-hash-key). |

## address-hash-key

SakuraBans matches address bans by a keyed hash of each address, and when a player is erased
(`/sb gdpr erase`) their punished addresses are kept only as that hash. Without the key, a hash
can't be turned back into an address by trying every IPv4 address.

- **A new install generates the key** into `storage.yml` the first time the file is created.
  The log says so; the key itself is never logged, stored in the database, exported or sent to
  the web editor. If the key comes from the environment (`SAKURABANS_STORAGE_ADDRESS_HASH_KEY`)
  when the file is first created, none is generated into the file.
- **Every server on one database needs the same key.** Copy the `address-hash-key` line from the
  first server's `storage.yml` to every other server, together with the connection settings.
- The database keeps a fingerprint of the key (which can't be turned back into it). A server
  whose key doesn't match refuses to start and says which line to copy; a `storage.yml` without
  the key, or with one shorter than 32 characters, is a configuration error. SakuraBans never
  writes an existing `storage.yml`, so add the line yourself.
- **Never change the key of a database in use**: no stored hash would match any more. Keep a copy
  of it with your backups; a database restored without its key can't be used.
- [`/sb import self`](/docs/guides/importing) from an installation with another key hashes the
  copied addresses again under this key. Erased addresses have nothing to hash again, so they no
  longer match; to keep them, give the new server the old key before its database is first used.

## pool

| Key | Default | Meaning |
|---|---|---|
| `pool.maximum-size` | `10` | The most connections open at once (1 or more). |
| `pool.minimum-idle` | `2` | Connections kept open while idle (0 up to `maximum-size`). |
| `pool.connection-timeout` | `5s` | How long to wait for a free connection. |
| `pool.max-lifetime` | `30m` | How long a connection is kept before it is replaced. Keep it shorter than the database's own connection time limit. |

## sync

| Key | Default | Meaning |
|---|---|---|
| `sync.mode` | `NONE` | How several servers on one database tell each other about punishments: `NONE`, or `SQL` (polling a table, for networks; needs MariaDB, MySQL or PostgreSQL). Without it, a mute or unmute from another server reaches a player within about a minute, and a ban from another server when the player next joins. |
| `sync.poll-interval` | `2s` | How often SQL sync checks for news, from 250ms to 30s. |

Sync orders its messages by the **database's clock**, so servers whose clocks disagree still
see each other's messages. Expiry and durations use each server's own clock, though: at startup
every server compares its clock with the database's and logs a warning when they are more than
5 seconds apart. Keep every server's clock synchronised (NTP).

See [Networks](/docs/guides/networks).
