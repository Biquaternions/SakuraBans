Containers and servers that share a mirrored folder often can't keep a different file per
server. SakuraBans reads the **file-level** settings from the process environment too, and the
environment **wins over the files**:

- `server.name`, `server.categories`, `web.token`, `geoip.enabled`, `geoip.account-id`,
  `geoip.license-key` and `geoip.refresh` of `config.yml`;
- every key of `storage.yml`, including the `address-hash-key`.

Nothing else is read from the environment. Settings that can be overridden in the database
(global and scoped ones) are changed with `/sb settings` or the [web editor](/docs/web-editor),
and the other file-only keys (`scopes.default`, `web.url`, `commands.labels`, ...) stay in
`config.yml`. A `SAKURABANS_` variable that names one of those, or anything unknown, stops the
start with a message that says where the setting lives. That includes typos, so don't give the
server unrelated variables that start with `SAKURABANS_`.

## One variable per key

`SAKURABANS_<PATH>`: the key's path in upper case, every `.` and `-` replaced by `_`, and
`STORAGE_` before the keys of `storage.yml`.

| Variable | Key |
|---|---|
| `SAKURABANS_SERVER_NAME` | `server.name` of `config.yml` |
| `SAKURABANS_SERVER_CATEGORIES` | `server.categories` (a list) |
| `SAKURABANS_WEB_TOKEN` | `web.token` *(secret)* |
| `SAKURABANS_GEOIP_ENABLED` | `geoip.enabled` |
| `SAKURABANS_GEOIP_ACCOUNT_ID` | `geoip.account-id` *(secret)* |
| `SAKURABANS_GEOIP_LICENSE_KEY` | `geoip.license-key` *(secret)* |
| `SAKURABANS_GEOIP_REFRESH` | `geoip.refresh` |
| `SAKURABANS_STORAGE_TYPE` | `type` of `storage.yml` |
| `SAKURABANS_STORAGE_H2_FILE` | `h2.file` |
| `SAKURABANS_STORAGE_HOST` | `host` |
| `SAKURABANS_STORAGE_PORT` | `port` |
| `SAKURABANS_STORAGE_DATABASE` | `database` |
| `SAKURABANS_STORAGE_USERNAME` | `username` |
| `SAKURABANS_STORAGE_PASSWORD` | `password` *(secret)* |
| `SAKURABANS_STORAGE_TABLE_PREFIX` | `table-prefix` |
| `SAKURABANS_STORAGE_SCHEMA` | `schema` |
| `SAKURABANS_STORAGE_PROPERTIES` | `properties` (a map) *(secret)* |
| `SAKURABANS_STORAGE_POOL_MAXIMUM_SIZE` | `pool.maximum-size` |
| `SAKURABANS_STORAGE_POOL_MINIMUM_IDLE` | `pool.minimum-idle` |
| `SAKURABANS_STORAGE_POOL_CONNECTION_TIMEOUT` | `pool.connection-timeout` |
| `SAKURABANS_STORAGE_POOL_MAX_LIFETIME` | `pool.max-lifetime` |
| `SAKURABANS_STORAGE_SYNC_MODE` | `sync.mode` |
| `SAKURABANS_STORAGE_SYNC_POLL_INTERVAL` | `sync.poll-interval` |
| `SAKURABANS_STORAGE_ADDRESS_HASH_KEY` | `address-hash-key` *(secret)* |

Values are written as in the files (`20`, `8s`, `MARIADB`, `true`). A **list** is comma-separated
(`survival,pvp`) or a JSON array. A **map** (`properties`) is a JSON object:
`{"useSSL": "true"}`. An empty variable sets an empty value.

## One JSON object

`SAKURABANS_CONFIG` holds one JSON object, like LiteBans' `LITEBANS_CONFIG`. Its keys are the
dotted paths (`storage.` before the keys of `storage.yml`), or nested objects:

```sh
export SAKURABANS_CONFIG='{
  "server.name": "survival-1",
  "server.categories": ["survival"],
  "storage": {"type": "MARIADB", "host": "db.internal", "pool": {"maximum-size": 8}},
  "storage.address-hash-key": "..."
}'
```

When both forms name a key, the individual variable wins over the JSON object.

## What the environment does and doesn't do

- **Checked like the files.** A value is read as if the file said it, so the same checks apply
  and an error names the variable (`SAKURABANS_STORAGE_PORT: "http" is not a number`, or
  `SAKURABANS_CONFIG[storage.port]` for the JSON form). SakuraBans doesn't start with an invalid
  value, and never repeats the text of a secret in a message.
- **The files are never rewritten.** They keep their comments and their values; the environment
  only changes what SakuraBans uses. `/sb reload` keeps applying it (the environment of a
  running process doesn't change).
- **A fresh install can get its `address-hash-key` from the environment.** If
  `SAKURABANS_STORAGE_ADDRESS_HASH_KEY` is set when `storage.yml` is first created, no key is
  generated into the file (it keeps the empty line), so the key exists in one place only.
  Every server on one database needs the same key either way; see
  [storage.yml](/docs/configuration/storage#address-hash-key).
- **Listed by name, never by value.** The startup log names the variables that apply, and
  `/sb settings list --effective` lists them with what they set; a secret (`web.token`,
  `password`, `properties`, `address-hash-key`) only says that it is set. Secrets from the
  environment are not stored in the database, not shown in `/sb status` or the instance list,
  and not sent to the web editor; the file-level keys never are.
- **Per process.** Each server reads its own environment. In a container, pass the variables
  with your orchestrator's secret mechanism rather than a file in the image.
