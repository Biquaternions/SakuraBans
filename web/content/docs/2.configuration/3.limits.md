`/sb reload` applies changes to `limits.yml`.

Staff are put in a **group** by its permission. The first group (in file order) whose
permission a staff member has applies to them; staff in no group have no limits. The console
and plugins are never limited.

- `sakurabans.limits.unlimited` ignores `max-duration` and `require-template`.
- `sakurabans.cooldown.bypass` ignores cooldowns.

| Key | Meaning |
|---|---|
| `reduce-to-limit` | Over a `max-duration`: `true` (default) shortens the punishment to the group's maximum, `false` refuses it. |
| `groups.<name>.permission` | The permission that puts staff in the group. |
| `groups.<name>.max-duration` | The longest ban, mute and warn, by type (`30m`, `7d`, `1mo`, ...). `permanent` or left out means no limit. A permanent punishment counts as longer than any limit. Kicks have no duration. |
| `groups.<name>.cooldown` | How long to wait between two punishments of a type (`ban`, `mute`, `warn` or `kick`). |
| `groups.<name>.require-template` | `true`: punishments need a template (`--template <name>`). Default `false`. |

```yaml
reduce-to-limit: true

groups:
  helper:
    permission: sakurabans.group.helper
    max-duration: {ban: 3d, mute: 1d, warn: 30d}
    cooldown: {ban: 30s, mute: 10s, warn: 10s, kick: 10s}
    require-template: true
  moderator:
    permission: sakurabans.group.moderator
    max-duration: {ban: 30d, mute: 30d}
    cooldown: {ban: 10s}
```

## Overrides

`limits:reduce-to-limit` and `limits:groups` can be overridden in the database like the keys of
`config.yml`: in global, in a category or for one server (the whole `groups` value is replaced,
never merged). A server without an override keeps using its own `limits.yml`, so the file keeps
working on its own. Edit them in the [web editor](/docs/web-editor) (Settings → Limits), where
groups keep their order, or publish a server's file values as global. On a network without
overrides, keep `limits.yml` the same on every backend: each server enforces its own copy.
