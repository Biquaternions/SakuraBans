`/sb` is `/sakurabans`; the labels can be changed in `commands.labels`. Commands marked
*confirm* first say what they would do and need the same command again with `--confirm`
within 30 seconds.

## General

| Command | Permission | Meaning |
|---|---|---|
| `/sb help [query]` | `sakurabans.help` | The commands you may use. |
| `/sb status` | `sakurabans.admin.status` | SakuraBans status, including the instances of the network it knows (the instance registry), and a reminder while `alts.auto-ban` waits for `/sb accept alts`. |
| `/sb accept alts` | console only | Accepts automatic alt bans once for the whole network (stored in the database): until then `alts.auto-ban` does nothing. |
| `/sb reload` | `sakurabans.admin.reload` | Reload the configuration and messages. Lists every problem if something is invalid, and the database overrides that exist. |

## Lockdown

| Command | Permission | Meaning |
|---|---|---|
| `/lockdown [-g\|--server\|--category\|--scope] [-d <duration>] [-r <reason…>]` | `sakurabans.admin.lockdown` | Keep new players out, everywhere or in a scope, optionally for a while and with a reason. |
| `/lockdown end [scope flags]` | `sakurabans.admin.lockdown` | End it. |
| `/lockdown status` | `sakurabans.admin.lockdown` | Whether a lockdown is active. |

`sakurabans.lockdown.bypass` lets a player join during a lockdown. `lockdown.persist` decides
whether it survives a restart.

## Allow list

Accounts and addresses that address bans don't reach. Both also pass the
[GeoIP](/docs/guides/geoip) country lists, and allow-listed accounts pass lockdowns.

| Command | Permission |
|---|---|

| `/sb allow remove <target>` | `sakurabans.admin.allow` |
| `/sb allow list` | `sakurabans.admin.allow` |

## Audit log

```
/sb audit [page] [--actor <name|uuid|console>] [--player <name|uuid>] [--id <id>]
          [--template <name>] [--setting <key>] [--action <action>] [--since <duration>]
/sb audit export [--actor …] [--player …] [--id …] [--template …] [--setting …]
          [--action …] [--since …]
```

Permission `sakurabans.admin.audit`, for players and the console. Every change SakuraBans makes
to punishments, templates, settings, messages, the allow list and players is written to the audit
log. `/sb audit` lists it newest first, ten to a page (give the page number before the flags,
`/sb audit 2 --action update`); the arrows keep the flags. Each line shows when, the action, the
subject, who did it (and from where: in game, the console, the web editor, a plugin) and a short
old → new summary. A line about a punishment clicks through to `/sb info <id>`. Filters combine:
every one you give narrows the result.

| Flag | Entries |
|---|---|
| `--actor` | made by this player, or `console` |
| `--player` | about this player (their erasure, address forgetting, allow-list entry, ladder uses) |
| `--id` | about this punishment (a number or a display id, as in `/sb info`) |
| `--template` | about this template, in any scope |
| `--setting` | that changed this settings key |
| `--action` | of this action: `create`, `revoke`, `edit_reason`, `edit_expiry`, `edit_scope`, `void`, `expunge`, `rollback`, `evidence_attach`, `evidence_detach`, `update`, `delete`, `forget_address`, `export`, `erase`, `allow`, `disallow`, `import`, `reset`, `apply` |
| `--since` | newer than this long ago (`7d`, `12h`) |

Every filter is answered by an index of the audit table, so a big log stays quick to query.

**Privacy.** Without `sakurabans.viewips` (and with `display.censor-ip-addresses` on), no
address is shown: older entries about address bans hold the address in their summary, and those
show as `203.0.*.*` like everywhere else. An address that has only a hash is shown as `address
<first eight characters of the hash>`, never as something that looks like an address. Secrets
(webhook URLs, the editor token) were never written to the log and show as `(secret)`. The
same rules apply to the audit lines of `/sb info`.

`/sb audit export` writes the matching entries as JSON to `exports/audit-<time>.json` in the
plugin's folder, reading the log in batches of 500 so a large log never sits in memory, and
replies with the path and the count. The file is masked like the list unless the console runs it.
Entries are objects with `id`, `at` (UTC), `actor` (`kind`, `name`, `uuid`, `source`), `action`,
`subjectType`, `subject`, `old` and `new`, newest first; the file ends with `count`.

[`audit.retention`](/docs/configuration/config#audit) deletes old entries by itself.

## Reset

```
/sb reset --mode <delete|deactivate|prune> [--scope <scope>] [--exclude <type>…] [--confirm]
```

Console only (LiteBans' `reset-database`, with more care). It first says how many punishments
it would touch and needs the same line again with `--confirm` within 30 seconds.

| Flag | Meaning |
|---|---|
| `--mode delete` | Remove the punishments and their history, with their evidence and their template uses (a ladder starts over for those players). |
| `--mode deactivate` | End every active punishment and keep the history (they show as ended by a reset). |
| `--mode prune` | Remove only the ended ones; active punishments stay. |
| `--scope <scope>` | Only this scope (`global`, `server:<name>`, `category:<name>`); default every scope. |
| `--exclude <type>` | Leave this type alone (`ban`, `mute`, `warn` or `kick`); repeat it for several. |

It runs in batches of 1,000, each its own transaction, so a large table doesn't hold one huge
transaction (if it fails part-way, run it again: finished batches stay done). One audit entry
records the mode, scope, types and count, not one per row. Mute caches and the range cache of
this server are reloaded, and the other servers of the network are told through sync to do the
same. Kicks are always "ended" (they are never active), so `deactivate` leaves them as they are.
