## Proxy only, or every backend

A network runs SakuraBans **either on the proxy or on every backend**, never both. With a
proxy-only install there is one instance and nothing below needs to match. The rest of this
page is about backends.

## Servers that let banned players in

A lobby, limbo or appeal server can stay open to banned players, so they can read why they
were banned or appeal (LiteBans calls this "lobby exclusion").

- **On a proxy**, list the servers in `enforcement.servers-without-login-check`. A banned
  player gets into the network, but only onto those servers: their first server is the first
  listed one, and every other server refuses them. They are told they are banned when they
  join, and staff aren't told of the join. When a ban is enforced on a player who is online,
  the proxy sends them to the first listed server that connects (then to its own fallback
  servers where the ban doesn't apply), and disconnects them if none does. A non-empty list
  checks every server switch, whatever `enforce-server-switch` says. Mutes still apply.
- **On backends**, set `enforcement.login-check: false` in that server's own `config.yml`.
  Banned players can join it, are told they are banned, and aren't kicked when a ban is
  enforced there. Which server a banned player reaches is decided by the proxy, not by
  SakuraBans: see the next section.

## Network kicks from a backend

When SakuraBans runs on the backends and a ban is enforced on an online player, the backend
kicks them, and the proxy then sends them to its fallback server (where, if that server
checks too, they are refused again). With `enforcement.network-kick: true` the backend asks
the proxy to disconnect them from the whole network instead, through the BungeeCord plugin
channel:

- the request is sent through the banned player's own connection (`bungeecord:main`, Paper's
  `BungeeCord` channel): first `KickPlayerRaw` with the screen as a JSON component, which
  Velocity reads, then `KickPlayer` with the screen as legacy text (colours kept, click and
  hover events lost), which every BungeeCord-style proxy reads;
- Velocity answers only with `bungee-plugin-message-channel = true` in `velocity.toml`;
- if the player is still on the backend 2 seconds later, or the proxy never registered the
  channel for them, the backend kicks them itself.

Only bans do this; `/kick` always kicks from the one server. It has no effect when SakuraBans
runs on the proxy. A banned player's *login* to a backend is refused before they are a player
there, so no plugin message can be sent: where the proxy sends them then (another server, or
a disconnect) is the proxy's decision, not SakuraBans'.

## One database

Point every backend at the same MariaDB, MySQL or PostgreSQL database with the same
`table-prefix` in [storage.yml](/docs/configuration/storage). They then share punishments,
players, alts, templates, the allow list and the audit log.

## Sync

Set `sync.mode: SQL` on every backend. Each one polls a table every `sync.poll-interval`
(default 2s) and learns about punishments issued elsewhere: an online player is kicked or
muted within seconds. Without sync, a mute or unmute from another server reaches a player
within about a minute, and a ban when the player next joins.

## What must match

| File | Key | Why |
|---|---|---|
| `storage.yml` | the connection (`type`, host, database, user) | Servers share punishments only through one database. |
| `storage.yml` | `table-prefix` | Another prefix is another set of tables. |
| `storage.yml` | `address-hash-key` | Addresses are matched by hashes under this key; a server with another key refuses to start. Copy it from the first server. See [storage.yml](/docs/configuration/storage#address-hash-key). |
| `storage.yml` | `sync.mode`, `sync.poll-interval` | Servers with sync off don't hear about punishments from elsewhere until the player rejoins. |
| `config.yml` | `scopes.categories` | Each server only knows the categories in its own file. |

## Clocks

Sync doesn't depend on the servers' clocks: messages are ordered by the database's clock.
Punishments still expire by each server's own clock, so a server whose clock is off ends a
punishment early or late. Each server compares its clock with the database's at startup and
warns when they differ by more than 5 seconds. Run NTP on every host.

## What should match

| File | Key | Why |
|---|---|---|
| `config.yml` | `enforcement.address-strictness` | Decides which accounts an address ban reaches. |
| `config.yml` | `alts.servers-without-ip-registration`, `alts.record-expiration` | Decide which address records exist and count. |
| `config.yml` | `exemption.*` | Otherwise staff are protected on some servers and not on others. |
| `config.yml` | `reasons.*`, `warnings.expire-after` | They shape what is stored when a punishment is issued. |
| `config.yml` | `display.id-style` | Staff would see different ids for the same punishment. |
| `limits.yml`, `webhooks.yml` | all | Each server enforces and posts with its own copy. |

## What differs on purpose

`server.name`, `server.categories`, `scopes.default`, `enforcement.enforce-server-switch`,
`enforcement.login-check`,
`enforcement.mute-command-blacklist`, `enforcement.login-check-timeout`, `commands.labels`,
`players.remote-lookup`, the `pool.*` settings, the `web.*` keys and the language files.

## Scopes and layers

Instead of keeping files in step, set values once **in the database**. Overrides are stored per
scope: **global**, a **category** (`category:<name>`) or one **server** (`server:<name>`). For a
server, the value of a key is the first of:

1. the override in its server scope;
2. the overrides of its categories, in order (the first category that has one wins);
3. the override in global;
4. its own file (`config.yml`, `limits.yml`, `webhooks.yml`);
5. the default.

A server's categories, in order: the categories of `scopes.categories` that list it, in the
order that map declares them, then the entries of its own `server.categories` that aren't among
them. `scopes.categories` itself is global-only, so every server agrees on it. A server with an
empty `server.name` has no server scope and only takes part in its own `server.categories`. A
scoped value replaces the whole value (a list or a map is never merged).

- **Global-only keys** must be the same everywhere and can only be overridden in global:
  `scopes.categories`, `scopes.require-permissions`, `enforcement.address-strictness`,
  `alts.record-expiration`, `alts.servers-without-ip-registration`,
  `alts.register-on-connection`, `exemption.*`, `display.id-style` and `lockdown.persist`.
- **Scoped keys** (everything else that is network-wide, plus
  `enforcement.mute-command-blacklist`, and the keys of `limits.yml` and `webhooks.yml`) can be
  overridden in any scope.
- **File-only keys** (`server.*`, `scopes.default`, `storage.yml`, `commands.labels`, `web.*`, …)
  are never overridden in the database. `server.name`, `server.categories`, `web.token` and
  the keys of `storage.yml` can be set per server from the
  [environment](/docs/configuration/environment) instead, which suits one mirrored folder.

A command or editor view that names no scope means **global**, never `scopes.default` (which is
only the default scope of punishments).

### Publishing

Overrides are sparse: a file is never imported by itself. To make one server's file values the
network's, **publish** them: the plugin shows the keys whose file value differs from the global
value, and writes the ones you confirm as global overrides. Secret values (webhook URLs) are
copied by the plugin and never shown.

### Commands

| Command | Does |
|---|---|
| `/sb settings list [scope]` | The overrides of a scope (global when none is named), with the file value beside each. |
| `/sb settings reset <key>\|all [scope]` | Removes an override, so the next layer applies again (`all` needs `--confirm`). |
| `/sb settings publish` | Shows the diff of this server's file values against global; with `--confirm` writes them as global overrides. |
| `/sb messages list [locale] [scope]` | The message overrides of a locale and scope. |
| `/sb messages reset <locale> <key>\|all [scope]` | Removes a message override. |

They need `sakurabans.admin.settings` or `sakurabans.admin.messages`. Startup and `/sb reload`
say which scopes apply to this server and how many overrides exist; nothing is overridden
silently. The [web editor](/docs/web-editor) edits every scope, shows each server's effective
configuration with the layer of every key, and publishes.

Messages are layered the same way, per locale: the server scope, its categories, global, then
the server's language file (then the `en_US` text, then the default).

Templates always live in the database and are shared automatically.

## Instance registry

Every server records itself in the database: its name, its categories, platform, plugin
version, when it was last seen, and its file values. Rows not seen for 7 days are removed.
`/sb status` lists the instances it knows, and the web editor uses the registry to offer real
server and category names, to show each server's effective configuration, and to publish a
server's file values.
