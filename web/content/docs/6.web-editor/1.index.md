The web editor edits what a network shares through its database: the overrides of `config.yml`,
`limits.yml` and `webhooks.yml` in every scope, messages per locale and scope, and templates. It works like LuckPerms' editor: no accounts,
no login, and the site never connects to your database.

## Setting it up

Set `web.url` in [config.yml](/docs/configuration/config#web). SakuraBans ships with **no
default address**: while `web.url` is empty, the editor commands only say that the editor
isn't set up, and everything is configured through the files as before.

:public-instance

If the site asks for an upload token, put it in `web.token`.

## The flow

1. Run `/sb editor` (or `/sb editor settings`, `messages`, `templates` for one section). The
   plugin builds a snapshot of what you may edit, encrypts it, uploads it and replies with a
   link, valid for a day by default.
2. Open the link. The page downloads the snapshot and decrypts it in your browser. Edit;
   every field shows where its value comes from (default, file or database override) and can be
   reset to the file value.
3. Click **Review and save**. The review lists every change in plain words; undo any you
   don't want. Saving encrypts the changes and uploads them.
4. The changes are applied in one of two ways:
   - **Live**: while the plugin is connected to the site (the header shows **Connected**), the
     server that created the session applies the saved changes by itself within seconds, and
     the page shows what was applied.
   - **By command**: otherwise the page shows `/sb applyedits <code>`. Run it in game or in the
     console of any server on the network. The code lasts an hour by default. Keep the dialog
     open and the result appears there once the command has run.

Nothing on the network changes until one of those happens.

## Scopes in the editor

Settings and messages are edited **per scope**: Global (the default view), each category and
each server the network knows, with how many overrides each has. A scope can be added by typing
a server or category name. In a scope, every key shows the value the scope inherits and where it
comes from (a category, global, the server's file); **Override here** turns it into an override
of that scope, turning it off removes the override so the key inherits again. Global-only keys
are read-only outside Global. The order of the layers is explained in
[Scopes and layers](/docs/guides/networks#scopes-and-layers).

- **Server view:** pick a server to see its effective configuration, with the layer each key
  comes from (click it to jump to that scope), and a warning where two of its categories set the
  same key, with the one that wins and why. Pending edits are included, so editing
  `scopes.categories` shows its effect at once.
- **Publish:** in Global, pick a server (by default the one that opened the editor) to see the
  keys whose file value differs from the global value, and tick the ones to publish. The plugin
  copies the values from its registry when it applies.
- **Limits and Webhooks:** two more tabs of Settings. Limits groups keep their order (the first
  matching group applies), with maximum durations, cooldowns and "needs a template" per group.
  Each webhook route is a card with its keys and a preview of the Discord embed, with sample
  placeholder values.
- **Secrets** (webhook URLs): the editor never receives them, only whether one is set. You can
  type a new value or clear it; it stays in the page's memory only (not in the tab's stored
  draft, so re-enter it after a reload), and the review, the outcome and the plugin's change
  lines never show it.

Templates have typed ladder steps (kick → mute → ban), shown as a chain, and a message for the
punished player per template and per step, with a preview; see
[Templates and ladders](/docs/guides/templates).

## Live apply

The server that ran `/sb editor` keeps a connection to the editor site open for the session.
The header of the editor shows:

| Indicator | Meaning |
|---|---|
| **Connected** | "Connected to the server: changes apply when you save." |
| **Not connected** | "Not connected: you'll get a command to run in game." This is normal, for example after the server stopped watching. |
| **Reconnecting…** | The page's own connection to the site dropped and is being restored. |

The server applies a live save **with the permissions of whoever opened the editor**, checked
again at that moment. It stops watching, for good, when no browser has connected within two
minutes, or none has been connected for two minutes; when the player who opened it leaves that
server; when the same person opens a newer session; when the session expires; or when the
plugin stops. From then on the command is the way.

Set `web.live-apply: false` if every change must be confirmed in game: the server then never
connects, and every save needs `/sb applyedits`.

## Who is told what changed

- The person who opened the editor sees one line per change in game (or in the console, if
  the console opened it), then conflicts and a summary, for example:

  ```
  Setting reasons.default: No reason specified → Breaking the rules
  Template hacking: changed reason (… → …), ladder, ladder-expiry
  Conflict: templates lifesteal changed meanwhile; not applied.
  Applied 7, unchanged 0, conflicts 1.
  ```

- With `/sb applyedits`, the person who ran the command sees the same lines, and so does the
  person who opened the editor (while online on the server that applied it).
- The editor page shows the same outcome.

## Conflicts and after an apply

The snapshot carries a version for each settings scope, for each messages scope and locale, and
for each template, so two scopes never conflict with each other. If someone changed one of them
on the server after the snapshot was taken, that part is a **conflict** and isn't applied
(every key of a conflicting scope is reported); everything else is. A change the server refuses while applying is reported as a
conflict too, with the reason.

## Keep editing after an apply

After every apply (live or by command, conflicts included) the plugin uploads a **fresh
snapshot** to the same link, and the editor switches to it by itself. Close the outcome and keep
editing: the link stays the same, and you don't need a new session.

When the fresh snapshot arrives, your pending edits are carried over:

| Your edit | After the refresh |
|---|---|
| The snapshot now has your value in that scope (or no override, for a removed one) | Dropped: it was applied. A new secret value is dropped when the result reports it applied. |
| Anything else | Still pending, against the new snapshot, so the next save uses the current versions. |
| An edit the plugin reported as a conflict, or whose server value changed meanwhile | Still pending, shown next to the server's current value; the notice says it changed on the server. Save it again to overwrite, or undo it. |
| An update of a template that was deleted on the server | Kept and flagged: saving recreates it; undo to discard your edit. |
| A new template whose name now exists on the server | Kept and flagged: saving replaces the server's; undo to keep the server's. |
| Edits in a section the fresh snapshot doesn't have (a permission changed) | Kept in the tab, but not sent; the editor says so. |

The refresh never moves the field you are typing in. With nothing of yours pending, it is silent,
apart from the "snapshot from" time in the header. Results of saves made in another tab, or by a
colleague with the same link, refresh the editor in the same way.

If the plugin couldn't upload the fresh snapshot, the editor keeps the one it has, marks the
sections that were changed as out of date (saving them again will probably conflict), and
suggests `/sb editor` for a new link.

If the plugin **refuses** a change set (an invalid value, a missing permission), nothing is
applied; the errors are shown next to the fields, and your edits stay pending.

Each save carries a sequence number, so a change set is never applied twice.

## What is sent to the site, and what isn't

**Sent, encrypted:** the settings you may edit (key, file, type, description, bounds, default,
level), their overrides per scope, the servers of the instance registry with their categories,
platform, version, last-seen time and file values, the message keys with their placeholders, the
language file texts of the uploading server and the message overrides per scope, the templates,
the names of known servers, categories and locales, the plugin version and platform, this
server's name, and the name and UUID of who opened the editor. Secret values (webhook URLs) are
never sent: only whether each is set.

**Never sent:** punishments, players, addresses, the audit log, `storage.yml` (database
credentials), `import.yml`, webhook URLs, and anything else not listed above.

## End-to-end encryption, in plain words

- The plugin makes a new random key for every session and puts it in the link after `#`.
  Browsers never send that part of a link to the site.
- Snapshot and changes are encrypted (AES-256-GCM) with that key before they leave the server
  or the browser. The site only stores encrypted data it can't read, deletes it after a day
  (snapshots) or an hour (changes), and holds no accounts.
- Only someone with the whole link can read the snapshot or produce changes the plugin will
  accept. Treat the link like a password.
- Changes still need the permissions in game: live applies use the opener's permissions, and
  `/sb applyedits` those of whoever runs it.
- The editor page loads nothing from other sites, keeps drafts only in your browser tab
  (`sessionStorage`, never the key), and sends no analytics.

## Commands and permissions

| Command | Permission |
|---|---|
| `/sb editor [settings\|messages\|templates]` | `sakurabans.editor` |
| `/sb applyedits <code>` | `sakurabans.editor` |

Each section also needs the node of its in-game administration:

| Permission | Section |
|---|---|
| `sakurabans.admin.settings` | Settings (including Limits and Webhooks) |
| `sakurabans.admin.messages` | Messages |
| `sakurabans.admin.templates` | Templates |

A section you may not edit isn't sent to the editor at all. A change set that touches a
section the applying person may not change is refused as a whole.

## Without the editor

Overrides are always visible and removable in game: `/sb settings list`, `/sb messages list`,
`/sb settings reset <key>`, `/sb messages reset <locale> <key>`. A network that loses its
editor site isn't stuck.
